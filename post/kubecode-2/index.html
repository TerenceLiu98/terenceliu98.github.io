🤓 Project Managers Don't Read Every Diff - 用 Kubecode Desktop 自举 Kubecode

30 Jul, 2026 · Updated 13 Sep, 2026 · Junjie LIU

Before

在上一篇文章里，我把 Kubecode 描述成一个 Agent Control Plane：用户不再坐在 editor 前面逐行写代码，而是定义目标、阅读 plan、验收结果，再把中间的 implementation 和 debugging 交给一支 agent team。那篇文章发出去的时候，Kubecode 仍然是一套 React frontend 加 Rust server，主要运行在 Linux、Kubeflow 或其他远端环境里。

后来我又新开了一个 repository：kubecode-desktop。

最省事的做法其实十分明显。Kubecode 已经有 React 和 Rust，只需要套一个 Tauri，理论上很快就能得到一个可以分发的 desktop application。但笔者恰好是 Mac、iPhone 和 iPad 用户，于是很自然地想试试：如果不用 WebView，而是认真做一个原生 Apple client，Kubecode 会长成什么样？

这不是一个完全理性的产品决策，更像是一次夹带私货的技术选择。结果也确实证明，夹带私货通常需要付出代价。

不过，Kubecode Desktop 现在已经可以做一件比展示 native controls 更有意思的事：用 Kubecode 开发 Kubecode。 我在 Desktop 里创建一个 Agent Session，和它讨论接下来要解决的问题，让它整理并提交一个完整的 GitHub Issue；目标明确以后，再把这个 Session promote 成 Team Leader，让它拆分 sub-issues、创建 teammates、分配 worktree、review diff、跑测试、提交 PR、等待 CI，最后 merge 和 close。

换言之，上一篇文章里画出来的流程图，已经开始拿它自己做实验了。

一个 Cloud-native 拥护者为什么开始写 Mac App

笔者一直是 cloud IDE 的长期用户。在 agentic AI 以前，我的大部分开发都通过 code-server 一类的工具直接发生在服务器上。本地电脑负责打开网页，代码、环境和计算留在远端。这对 research 尤其合理：科研代码通常不需要频繁对接摄像头、窗口系统、系统权限或者其他本地硬件，反而很依赖服务器上的数据、GPU 和长时间运行的任务。

但 Kubecode Desktop 本身是一款 macOS application，而服务器上没有 macOS。SwiftUI、AppKit、窗口行为、键盘交互、系统权限、Keychain、签名和打包都必须在真实的 Mac 上调试。于是从第一天起，我就没有机会先在 cloud IDE 里试错，只能在本地启动 App，再盯着窗口看它究竟做了什么。

这种 feedback loop 的确很方便。修改代码、启动 App、马上观察滚动和布局，不需要再穿过浏览器或远端桌面。但我并没有因此突然成为 local-first 的信徒。恰恰相反，我仍然很想把开发迁回远端：手上的 M1 Pro 配 512 GB 存储已经逐渐不堪重负，编译产物、依赖和几个同时运行的 agents 很快就会把本地机器塞满。只是既然选择了原生 macOS 开发，这部分工作暂时没有地方可以搬。

为什么不及时止损，回去做 Tauri？一方面，原生 App 的资源占用确实低，窗口、菜单、快捷键和系统行为也更像一款真正长期运行的 Mac workstation；另一方面，这是我第一次认真体验 macOS 原生开发。既然已经走进来了，我不打算因为第一个难题比预期麻烦，就马上从入口退回去。

事实证明，第一个难题不是一般的麻烦。

一个聊天框为什么从 SwiftUI 走到了 NSCollectionView

Agent 的输出通常是 Markdown。听起来只需要把一段字符串放进界面，实际上它很快会变成：

Markdown
+ LaTeX
+ code block
+ table
+ font / baseline alignment
+ text selection
+ streaming update
+ long transcript virtualization
+ stable scroll position

最初的版本使用 SwiftUI Text 拼出 Markdown。它不支持我需要的 LaTeX，于是又接入 SwiftMath；公式出现以后要解决 font 和 baseline 对齐；表格、代码块和选择复制又各自带来新的布局要求。短对话里这些方案都可以工作，看上去只是一个 feature 接着一个 feature 补上去。

等对话变长，CPU 占用和卡顿才一起出现。每次滚动都可能触发位置测量与重新渲染，而流式 token 又在不断改变内容高度。实现也从 SwiftUI 走到 NSTextView，最后再走到 NSCollectionView，试图用更明确的 row ownership、height cache 和 virtualization 控制 transcript。

目前仍然没有一个让我满意的答案。为了减少流式阶段的重排，Kubecode Desktop 暂时不会在每一个 token 到达时完成完整的 Markdown 排版，而是等 response 结束以后再一次性渲染。这个妥协既牺牲了 streaming Markdown 的体验，也没有彻底解决长 transcript 滚动时的错位，所以当然不算“已经解决”。

问题的一部分也来自我并不是专业 Apple developer。当 agent 给出一套听起来合理的 SwiftUI / TextKit / Collection View 方案时，我缺少足够经验判断它是在修真正的 ownership 问题，还是给上一层 workaround 再盖一层 workaround。结果就是 agent 可以持续产出局部正确的代码，而整个 renderer 越走越远。

现在我的办法是先找已经跑通的 reference implementation，让 agent 阅读源码，而不是从空白处替我推导一套 Apple UI architecture。微软的 SwiftStreamingMarkdown 是目前正在考察的候选：它本来就面向 LLM streaming，支持增量 Markdown、LaTeX、table 和 code block。至于直接替换现有 renderer，还是只借鉴它的实现，再保留 Kubecode 自己的 transcript virtualization，目前还没有结论。

微软不愧是 App Store 最佳开发者。

Kubecode 开始开发 Kubecode

原生 UI 仍然有坑，不妨碍 Desktop 已经进入真实工作流。我目前最常用它做的项目，就是 Kubecode 本身。

一次比较完整的自举流程是：

创建一个 Solo Agent
        ↓
讨论接下来真正需要解决的问题
        ↓
Agent 整理完整 Issue，并提交到 GitHub
        ↓
Promote 原 Session 为 Team Leader
        ↓
Leader 拆分有依赖关系的 sub-issues
        ↓
Teammates 在独立 worktrees 中实现
        ↓
Leader review diff、运行测试并整合
        ↓
Leader 创建 PR，等待 CI，通过后 merge / close

例如 Runtime event delivery 的 Issue #1，先把 durable event bus、SSE wakeup、Runtime status、browser batching、reconnect recovery 和 UI 拆成一组有顺序的 sub-issues，最后由 PR #8 集中完成。另一个 typed Composer 设计，则先调研 Cindy、Orca、Zed、Kilo 和 Copilot ACP，再定义 @ context、/ command、$ capability 的边界，写 ADR，然后沿依赖关系逐个推进 server catalog、context resolution 和 structured draft。

这里所有 PR、commits、CI、merge 和 issue closing 都由 Leader 完成。Teammates 不直接挤在同一个目录里改代码，而是在不同 worktrees 里执行自己的任务；完成以后向 Leader 汇报，Leader 查看 diff、运行测试，认为不合格就打回修改，认为可以接受才进入 PR 和 CI。

笔者一般不介入这个过程。我负责定义问题、回答澄清问题、阅读 plan 和 acceptance criteria，再判断 agent 给出的方案是不是我想要的。如果可以，我也会要求流程图、表格或者其他能暴露结构的 artifact。方向确定以后，我不会逐行阅读 Rust diff，也不会旁听 Leader 与 teammate 的每一句沟通。

这不是 Kubecode 缺少 transparency，而是它有意提供的一层 abstraction。Project manager 本来就不需要参加工程师之间的每一次讨论。他需要知道谁在做什么、结果为什么被打回、测试是否通过，以及最后交付的东西有没有达到目标。Kubecode 的目的也不是让科研民工更方便地 micromanage 一群 agents，而是让他终于可以少管一点工程细节。

当然，这套信任对不同任务并不一样。Runtime、API 和状态机可以写成 acceptance criteria，再由 tests 和 CI 反复验证；聊天滚动错位这种 UI 问题，即使所有测试都是绿色，打开 App 以后仍然可能一眼看出不对。现在的工程功能已经有一条相对稳定的 evidence chain，UI 仍然主要依靠参考产品、真实运行和我的 taste。以后也许应该在实现之前加入 prototype、固定 viewport screenshot 或 interaction recording，但目前还没有做到。

统一 Team，不统一 Agent

Kubecode 支持 Codex、Claude Code 和 OpenCode，并不是因为我想把它们抹平成三个只有 logo 不同的 chatbot。用户喜欢的是不同 agent 产品已经迭代很久的 harness：各自的认证、model、mode、plan、permission、skills、session resume 和工具行为。重新调用模型 API，再实现一套“统一 agent”，等于主动丢掉用户已经习惯的部分。

因此 Kubecode 统一的是 Team 的构建和管理，不统一 agent 本身。Project、Session、Team、成员、任务依赖、worktree、mailbox 和 lifecycle 可以由 Kubecode 管理；每个 agent 怎样规划、调用工具、使用 skills 和完成任务，仍然留给它自己的 harness。Memory 和 Session persistence 也可以在底层统一，但这些不应该成为用户需要手工维护的工作。

实际自举中，Leader 一般是我最习惯使用的 Codex。Team 里也出现了 Claude Code teammate，不过它背后接的模型是 GLM 5.2。原因并没有复杂到需要一个 routing paper：我刚买了 GLM Max Plan，正好想在真实任务里试试它的能力。Leader review 以后确实会把方案打回去修改，但由于我不阅读每一段内部对话，目前也无法把最终质量精确归因到 GLM、Claude Code harness 或 Codex Leader。

这种组合至少说明了一件事：Kubecode 调度的单位不是一个抽象的 model name，而是 harness × model × role。未来可以把昂贵、可靠的模型放在 Leader 位置，把局部实现交给 GLM、DeepSeek 等更便宜的 teammates，理论上降低整个 Team 的成本。但这里需要诚实一点：我还没有记录和比较相同任务的 token、时间与返工次数，所以“异构 Team 更便宜”目前仍然是设计动机，不是实验结论。

Local Agent，Remote Workspace

做 Desktop 还有一个比原生 UI 更根本的原因。

如果 Kubecode 只运行在服务器或 Kubeflow Pod 里，用户就需要在每一个环境里重新安装、登录和配置 Codex、Claude Code 或 OpenCode。Agent 的网络连通性、版本、credentials 和资源占用，也顺手变成了服务器管理员的问题。但用户自己的电脑上往往早就配置好了这些工具。省事才是重点：为什么不能直接复用本地 agent，再通过 SSH 或 kubeconfig 使用远端计算？

理想状态应该是：

本地 Agent
    ↓
Kubecode Workspace Tools
    ↓
Remote Runtime
    ↓
远端 Files / Git / Terminal / Compute

这里必须区分目标和现实。当前 local_managed 模式中，Agent、Runtime 和 workspace 都在本地。仓库已有的 ssh_managed 路径则会通过 SSH 在远端启动 kubecode-server，再建立 loopback tunnel；由于 Agent 仍由 Runtime 管理，所以 Agent 和 workspace 都在远端。kubeconfig 也还没有实现。真正的“本地 Agent 操作远端 workspace”仍处于设计阶段。

一开始我想到的是 VS Code Remote SSH。它在本地保留 VS Code UI，在远端安装 VS Code Server；文件、terminal、language server 和大部分 workspace extensions 跟着 workspace 在远端运行。它真正有价值的不是 SSH 命令，而是一套 location-transparent workspace API：扩展调用的是 workspace 能力，VS Code 再决定这些能力在本地还是远端执行。具体架构可以参考 VS Code 的 Remote SSH 和 Remote Extensions 文档。

Kubecode 可以沿着同一个方向，为远端文件、Git、terminal 和 process execution 提供 MCP server。这样本地 Agent 至少能够“知道”远端能力存在。问题是 MCP 只解决 capability discovery，还没有解决 capability routing。Codex 或 Claude Code 可能同时看到原生的本地 shell 与 Kubecode 的 remote_exec；即使 system prompt 告诉它当前是 remote project，它仍然可能在某一次工具选择里回到本地。若本地恰好存在同名路径，这种错误甚至不会立即失败。

所以真正困难的问题是：怎样让这一切对 agent 无感？是通过 prompt 要求它自觉使用 MCP；在 Remote Session 中隐藏或禁止本地 file / shell tools；还是深入每个 adapter，把 provider-native tool call 重写到 Remote Runtime？第一种不可靠，第二种可能损失 harness 能力，第三种又意味着需要长期维护 provider-specific integration。这个问题目前还在调研，我没有打算先写一个漂亮的架构图，再假装它已经可以运行。

这也会是 kubecode 接下来最重要的工作。集群只提供计算，本地保留用户已经配置好的 agent，听起来十分自然；怎样跨过文件系统和 shell 的边界，同时又不破坏各家 harness，才是这句话真正昂贵的部分。

Project Manager 不需要看每一个 Diff

在上一篇文章里，我写道：AI 不应该替研究者提出问题，但可以补上研究者一直缺少的那支工程团队。自举开发并没有推翻这句话，反而让它变得更具体。

Daniel Litt 在 Mathematics in the Library of Babel 里区分了两件事：证明一个已经被提出的 lemma，与发现关键 lemma 究竟应该是什么。现有模型已经越来越擅长前者，也许很快会解决真正重要的 open problems；但提出有意义的定义、建立 theory、判断什么值得理解，仍然远弱于它们解决 well-posed task 的能力。Vishal Misra 在 AI Can Prove Theorems. It Can’t Pick Which Ones Matter 中把类似区别描述为在已知框架中 filtering，与选择甚至发明框架本身。 这不是一个“AI 永远无法提出 idea”的不可能定理。LLM 已经可以生成看起来新颖的候选方向，未来能力也会继续变化。对 Kubecode 来说，更务实的判断是：至少在今天，研究者最应该保留的是选题、taste、问题定义和结果判断；agents 已经足够擅长接管从明确问题到可验收 artifact 之间的大量工程工作。

我已经开始把 Kubecode 用进自己的 research，但还没有一个足够完整、可以拿出来复盘的案例。因此这篇文章不打算宣布科研闭环已经被验证。那会是下一篇 blog 的重点。

而至于移动端， 应该也暂时遵循类似边界。iPhone 和 iPad 这种小型移动设备更适合查看正在运行的 Team、处理 permission、补充澄清和做小幅调整，而不是在路上开启一个新的工程任务。具体产品形态还没有想好，但它应该是 ongoing work 的 companion，不是把整个 workstation 缩进一块更小的屏幕。

下一步是什么？

Kubecode Desktop 已经可以承担本地项目的真实开发，也已经用 Solo Session → Team → worktree → PR → CI → merge 的流程开发了 Kubecode 自己。它还不是完整替代 Web 版的客户端，例如 Session promote 成 Team Leader 以后，Desktop 不能再随意插入普通对话；不过真正需要用户澄清时，Leader 会进入 Needs Attention，通过专门入口请求回答。这类 parity 缺口目前并不妨碍核心 loop。

接下来两个 repository 各有一个很具体的问题。

  1. kubecode 要解决的是本地 Agent 如何通过 MCP 无感操作远端 workspace。MCP 可以把远端能力暴露出来，但怎样确保 agent 不会误用本地工具，仍然没有答案。
  2. kubecode-desktop 要解决的是 streaming Markdown。当前 turn 结束后再完整渲染的妥协不可接受，滚动错位也没有消失；下一步需要重新评估 renderer，而不是继续在现有方案上无限补丁。

至于异构 Team 是否真的更便宜、Leader 的 review 能否长期挡住便宜模型的错误、这套流程能否完整推进一个 research project，都还需要真实使用和数据。现在唯一已经发生的，是我打开 Kubecode Desktop，定义一个问题，然后看着 Leader 带着 teammate 把它变成 Issues、commits、tests 和 merged PR， 等等。 Project manager 不需要知道工程师之间说过的每一句话，也不需要阅读每一个 diff。他需要定义问题，判断方案，并对最后的效果负责。给科研民工配一支工程团队，大概就是先从允许他少管一点工程开始。
